# Native feature HID and ENE transaction boundary

`feature_hid.rs` is an injectable policy layer around the independently C++-checked Fusion2/Valkyrie controllers. `feature_hid_windows.rs` contains the dormant native backend; only explicit runtime factories can construct it. `ene_bus.rs` is a stateful boundary over an injected executor/mutex, not a native PawnIO backend. Existing protocol/source hashes are recorded in the adjacent fusion2/valkyrie/ene/pawnio provenance files.

## Windows contract

Local primary header read2026-11-06: Windows SDK10.0.26100.0 `shared/hidclass.h:135–158`, SHA-256 `25dce618f29081a8a389bbef58fdf54af9525eafea02789264071062fbfa0455`. It defines HID_IN_CTL_CODE(100) for SET_FEATURE, HID_OUT_CTL_CODE(100) for GET_FEATURE. `shared/devioctl.h` defines FILE_DEVICE_KEYBOARD11, METHOD_IN_DIRECT1/METHOD_OUT_DIRECT2 and ANY_ACCESS0. Calculated user-mode codes are0xB0191/0xB0192; the header itself is not redistributed.

Successful SET returns class Information0, not a physical byte count: [Microsoft IOCTL_HID_SET_FEATURE](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/hidclass/ni-hidclass-ioctl_hid_set_feature). The Rust adapter returns its logical controller report size after this successful API completion; this is Submitted, never a physical LED acknowledgement. Feature GET uses the Windows hidapi normalization of count+1 only for report ID0: [official hidapi Windows implementation](https://github.com/libusb/hidapi/blob/master/windows/hid.c). Bounds and response ID are checked before copying to the controller packet. SET is padded to the descriptor maximum as hidapi does. Fusion2's64-byte logical packet is accepted with complete feature descriptors64..4096 containing only reportIDCC; tests64/65/96/4096 use fake descriptors and do not establish physical compatibility. Other report IDs and larger maxima are explicitly unsupported pending evidence. Keyboard remains exactly65/reportID0, with MI02/03 from its validated path. Input/output report caps are not guessed or required because these controllers use features.

Native requests keep their buffer, event and OVERLAPPED until completion or CancelIoEx plus blocking GetOverlappedResult drain: [Microsoft cancellation lifetime requirements](https://learn.microsoft.com/en-us/windows/win32/fileio/canceling-pending-i-o-operations). Timeout is nominal250ms with cancellation checked at most every25ms during pending waits; a broken kernel driver can make final drain unbounded. Freeing its live request would be unsafe. The private starter callbacks must return the immediate FFI result and must not retain pointers or panic after submission.

The native factory validates family/path, known competing-writer names, metadata attributes/all feature value+button capabilities, exclusive opening and descriptor equality. This is not a claim to identify every external writer. An unavailable exclusive handle or unknown capability fails without stopping other programs. No native metadata handle, physical HID path or live feature operation was used in this stage.

## Stand coverage and limits

`feature_hid` fake-backend tests run complete Normal/Pro transactions through the actual packet controllers, retain one wire allocation across reports, exercise every12operation failure position, and reject malformed count/ID/caps/paths/late writer/commands/cancellation before later I/O. Valkyrie phase/key maps/padding/control packets and Fusion2 owned count nibbles/direct mask/data spans are checked before raw execution. Errors close the link and do not retry.

`feature_hid_windows` tests create unique local named pipes and never enumerate/open hardware: successful TransactNamedPipe completion, pending timeout/activecancel with common wait/drain, and the expected DeviceIoControl feature-code failure on a pipe. These test actual Windows async request lifetime, not a successful physical HID feature ABI. Physical/global-mode readiness and performance remain UNKNOWN.

`ene_bus` tests use the actual Rust ENE controller over fake executor/mutex. The entire transaction holds the shared guard. Pointer/destination/direction/value bounds reject identity/config writes, persistent applyAA, SPD/remapping and RGB overflow. Read results with high bits beyond255 are deliberately rejected rather than silently truncated; that exact pinned-module ABI property remains UNKNOWN. ByteOnly mode declines a block before execution, so fallback proves no progress; generic errors never imply unsupported. A future native executor must verify the pinned module/provider/primary port under the same global mutex and implement bounded I/O; those operations are not implemented here.

Final224tests debug/release and all-target Clippy-Dwarnings passed; logs, hashes and bounded review are in ignored `work/feature-hid-stand`. Tests do not prove whole-product completion, physical support, measured FPS or CPU/RAM savings. Working cooling, applications, network and OS power were unchanged.
